## I — 方法论骨架 (Interpretation)

公开大模型跑分榜（及「鹈鹕骑自行车」、炫酷 Three.js 演示）已普遍被厂商针对性后训练、刷榜与 OpenRouter 用量污染，无法指导真实工程选型；与此同时，盲目在所有场景下混用便宜模型或单一高端模型，要么在核心代码库里埋下「早期智商债」（低水平模型写出的错误文档被后续强模型盲信并继承放大），要么在企业交付中因海外接口 403 封号、网络抖动或激进上下文压缩而翻车。

本方法论将「模型怎么测」与「算力怎么分」统一为一套工程化体系：
1. **三维硬核实测法（怎么测真水平）**：
   - **产物性能计分（后端）**：不看刷题正确率，直接让模型从 0 实现一个完整可运行的工程产物（如向量数据库 `vector-db-bench`），按编译后产物的实际吞吐/延迟性能排名，且严格固定统一的 `reasoning_effort` 档位（拒绝为特定模型单独调档作弊，警惕过度思考先升后降的陷阱）。
   - **6 次连抽一致性（前端与防量化鉴定）**：同一套复杂前端 Prompt 连续抽卡 6 次，横向比对实现细节与依赖版本指纹（如 Three.js 是否停留在旧版 r160 以前）；6/6 全稳才算合格，并可据此识别模型是否为某旗舰模型的蒸馏/量化版。
   - **超长真实日志与多智能体游戏压测（Agent 极限）**：用 260MB（120 万条）真实提权攻击日志压测 Agent 的 Harness 循环分担能力（避免把「用脚本循环 10 次」错写成让模型在上下文里手算 10 次而耗尽预算），或用打怪/召唤 SubAgent 团战堵门游戏观察多智能体自发协作水平。
2. **场景隔离与协议解耦路由（怎么分算力）**：
   - **长线核心代码库 → 锁死 SOTA + 极简 Points**：主架构与长线商业项目坚持使用 SOTA 模型（如 Opus 5.5 / Astra / Fable 5.1），且绝不让 AI 生成冗长 Spec 文档，只记关键 Points，为未来模型升级保留系统「自愈」空间。
   - **日常编码与本地 Agent → 顾问分层 + 量化黄金组合**：日常编码用便宜快速的执行模型干活，仅在定方案前、同一错误反复出现、宣布完成前开启顾问模式（如 `/advisor opus`）请旗舰模型把关；本地单卡部署 Agent 则按「8 模型 × 4 量化 × MTP 开关 × 思考档位」矩阵实测选出甜点组合（如 `Qwen3.8-27B-UD-Q4_K_XL` + `reasoning_effort=low`）。
   - **ToB 企业客户交付 → 锁死高稳定国模**：给传统企业做交付时，稳定性优先于极限智力，基模锁死 DeepSeek 或 GLM 系列，杜绝客户早起遇到 403 或降智。
   - **客户端与底层模型解耦**：通过本机协议翻译代理（如 OpenCodex 在本地 `10100` 端口将 Responses API 与 Chat Completions 双向转换）或集中配置表（如 `magpie` 统一管理各 Agent 的 `provider/model`），实现「界面与工具链不换，底层模型一键热切」。

## A1 — 应用示例 (Application Example)

### 示例 1: 用「从 0 写向量数据库 + 前端 6 连抽 + 260MB 日志」实测新模型
- **类型与来源**: 原书实操案例（`@karminski3` `2026-08-27` / `2026-08-31` / `2026-09-14` / `2026-09-22` 帖文）
- **问题/输入**: 面对层出不穷的新模型（Fable-5.1、Opus 5.5、DeepSeek-v4.1-Flash-1017、Qwen3.8 系列）与官方高分宣传，需要判断其在真实后端编码、前端稳定性、量化部署与长程 Agent 任务中的真实表现。
- **方法论的使用**:
  1. **后端评测**：统一 `reasoning_effort` 口径，让各模型从 0 编写向量数据库并跑 `vector-db-bench` 测实际性能；
  2. **前端与同源鉴定**：对 Opus 5.5 与 Fable 5.1 用同一套前端提示词各连跑 6 次比对产物；
  3. **小模型矩阵横评**：在单卡 H100 NVL + `llama.cpp` 上对 8 款模型 × 4 种量化 × MTP 开/关 × `low/medium/xhigh` 三档做全矩阵测试；
  4. **Agent 日志压测**：将 Zenodo 上 120 万条（约 260MB）真实提权攻击日志交给 Apodex 1.1 / DeepSeek-v4.1-Flash，观察其是否通过编写 Harness 脚本循环排查攻击并生成防火墙规则。
- **结论**: Fable-5.1 写出的向量数据库性能约为第二名的 2 倍；Opus 5.5 前端 6 次抽卡 6 次高度同质且全稳（据此判断其极可能是 Fable 5.1 的量化/蒸馏版）；本地 Agent 最优性价比组合为 `Qwen3.8-27B-UD-Q4_K_XL` + `reasoning_effort=low`；DeepSeek-v4.1-Flash 后端跃升至国产旗舰水平，但 Agent 训练得过于「抠门」（预算计数易退化）。
- **结果**: 产出了可公开复现的 `vector-db-bench` 榜单与 `deepseek-v4.1-flash-1017-issue-pov` 故障复现仓库（含 `AGENT-CAPABILITY-REPORT.md` 与 `log-replay` 探针），成为开发者选型硬核参考。

### 示例 2: 长线商业 App 防「早期智商债」与日常 `/advisor` 高低混搭
- **类型与来源**: 原书实操案例（`@waylybaye` `2026-09-17` / `2026-09-23` 帖文 + `@bozhou_ai` `2026-11-02` 帖文）
- **问题/输入**: 独立维护多款长线商业 App 时，若图便宜用次级模型写代码和长篇 Spec，旧模型留下的事实错误会被新模型当成金科玉律继承放大；但若全天候无脑跑最高档模型，部分模型（如 Fable 5.1）一天就会烧掉 85% 的周额度。
- **方法论的使用**: 在核心代码库严格执行「防早期智商债」原则——主力架构与复杂 3D/UI 锁死 SOTA 模型（Opus 5.5 / GPT-6 Astra），且禁止 AI 生成长篇 Spec，文档只记关键 Points；在常规功能迭代中采用分层路由——平时让高性价比的 Sonnet 执行编码，开启 `/advisor opus` 仅在「定方案前、同一错误反复出现、宣布完成前」三个关键节点自动请 Opus 出主意，完事后 `/advisor off`。
- **结论**: 架构决策与文档留存必须用最高智商模型保底线、留白促自愈；常规搬砖则用「执行模型 + 顾问模型」按节点切分算力。
- **结果**: 既避免了代码库被低质量 Spec 污染，又将高昂的 Token 消耗控制在合理水位（如 `@bozhou_ai` 实测 $20 套餐配合顾问模式比无脑消耗耐用数倍）。

### 示例 3: ToB 企业交付锁死稳定国模 + OpenCodex / magpie 本机协议解耦
- **类型与来源**: 原书实操案例（`@cnzhihao` `2026-11-03` 帖文 + `@sitinme` `2026-10-31` 帖文）
- **问题/输入**: 一方面，给传统企业客户交付业务 Agent 时，海外模型偶发的 403 封号、网络断连或激进上下文压缩（如 `@icycat` 实测某模型三句话压缩一次上下文）会导致客户业务停摆；另一方面，开发者习惯了 Codex 或 Claude Code 的顺手终端界面，但 Codex 强绑定 OpenAI 专属的 `Responses API`，无法直接接入其他高性价比或高稳定模型。
- **方法论的使用**:
  1. **ToB 生产环境**：严守「稳定性比模型智能重要一万倍」铁律，面向企业客户的底层基模统一锁死为国内高可用 API（DeepSeek 与 GLM 系列），配合 DeepSeek Harness 插件直连企业数据库；
  2. **本地研发环境**：在本机 `10100` 端口部署 `OpenCodex` 本地代理，自动把 Codex 发出的 `Responses API` 请求与第三方模型的 `Chat Completions` 协议做双向翻译，或在 `magpie` 的 Agent 管理面板中用一张表集中绑定所有 Agent 的 `provider/model`。
- **结论**: 生产交付看 SLA 稳定性，本地研发看工具链解耦；通过本地协议网关即可兼得最强 Agent 外壳与任意底层基模。
- **结果**: 企业客户早起使用零 403 故障，开发者在本地无需更换编码界面即可一键秒切全网模型。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?
1. **新模型/新 Agent 验真与自建 Benchmark**：刚出了一款新开源/闭源大模型，用户不信官方跑分和演示视频，想设计一套能测出真实编码能力、前端稳定性、量化损耗或长上下文 Agent 能力的压测方案。
2. **怀疑模型降智、偷换量化或上下文缩水**：用户感觉常用的模型突然变笨、前端代码反复出错，或者想确认某中转 API / 新模型是不是旧模型的蒸馏量化版。
3. **多场景算力选型与 Token 成本优化**：用户在纠结长线核心项目、日常小工具开发、本地显卡部署（llama.cpp / MLX）以及 ToB 客户交付分别该选什么模型、开什么思考档位（`reasoning_effort`）。
4. **Agent 客户端与底层模型解耦**：用户想在 Codex、Claude Code 等强绑定特定接口协议的 Agent 工具里无缝换用其他厂商的模型。

### 语言信号 (用户的话里出现这些就应激活)
- 「怎么测这个新模型到底行不行」「怎么搭自己的 benchmark」「官方跑分能信吗」
- 「这模型是不是降智了 / 蒸馏版」「怎么测模型稳定性」「reasoning_effort 选哪档」
- 「什么是早期智商债」「怎么省 token 又不降代码质量」「ToB 交付选什么基模最稳」
- 「怎么给 Codex 换别的模型」「OpenCodex 怎么配」「怎么统一管理多个 Agent 的 provider 和 model」

### 与相邻 skill 的区分
- 与 `agent-software-factory` 的区别：`agent-software-factory` 关注「选好模型之后，如何用 Worktree、E2E 录屏和 Pre-commit Hook 组织并发软件研发流水线」；本能力卡关注「如何评测模型真伪优劣、如何防范早期智商债、以及如何在不同任务间路由模型与解耦协议」。
- 与 `enterprise-fde-and-one-person-ops` 的区别：`enterprise-fde-and-one-person-ops` 关注企业 FDE 的商业报价（5–8 万地基成本）、20 人天上限与三层报错流程；本能力卡仅负责其中的底层模型 SLA 选型与算力路由策略。

## E — 可执行步骤 (Execution)

**必需输入**:
- `task_goal`（必填，枚举：`benchmark_design` [设计模型/Agent 实测] | `model_routing` [场景选型与成本路由] | `protocol_decoupling` [客户端换脑解耦]）
- `context_constraints`（必填：若为评测，需提供目标领域［后端/前端/本地量化/长日志 Agent］与可用算力；若为选型路由，需说明项目生命周期［长线核心库/短期探索/ToB 交付］与预算上限）
- 缺失上述任一关键维度时，先向用户确认，不得盲目推荐单一模型。

**交付物与完成标准**:
- 可复现的压测方案（含固定参数口径、抽卡次数与判分指标）、分场景模型路由表（含防范早期智商债规范）、或本机协议解耦配置步骤。

当此能力被激活后，按以下步骤执行：

1. **按目标场景分流执行核心方案**
   - **如果 `task_goal == benchmark_design`（设计模型与 Agent 压测）**：
     1. **锁死统一测试口径**：固定所有参测模型的 `reasoning_effort` 档位（严禁为某模型单独调高/调低档位），记录精确的依赖库版本指纹（如检查生成的 Three.js 版本号是否滞后）。
     2. **后端能力测产物性能**：设计「从 0 实现一个闭环系统（如轻量向量数据库或编译器组件）」的任务，不按代码外观打分，而是用固定基准脚本跑出编译后产物的 QPS / 延迟数据排名，并在报告开头声明「结论仅代表本测试场景」。
     3. **前端能力测 6 次连抽一致性**：同一 Prompt 连续独立运行 6 次，记录成功运行率与实现细节方差，满 6/6 一致方可标记为生产可用。
     4. **Agent 能力测大数据量 Harness 分担**：准备百万行级真实日志（如 260MB 攻击日志）或多角色协作游戏环境，检验 Agent 是否懂得编写外部循环脚本（Harness）处理数据，而非在单线 Thinking 中硬塞上下文导致注意力崩溃或因「抠门」提前终止。
     5. **本地量化测四维矩阵**：若评估本地模型（`llama.cpp` / `MLX`），按「模型尺寸 × 量化精度（如 `UD-Q4_K_XL`）× MTP 开关 × `reasoning_effort`（`low/medium/xhigh`）」建立测试矩阵，找出不掉点且开启 MTP 可提速的最优档位。
   - **如果 `task_goal == model_routing`（场景选型与算力路由）**：
     1. **长线核心代码库（防早期智商债模式）**：强制路由至当前 SOTA 模型（如 Opus 5.5 / GPT-6 Astra）；同时立下文档铁律——严禁让 AI 生成长篇设计 Spec，所有架构文档只记录人类确认的关键 Points，防止模型生成的隐蔽谬误被下一代模型盲信放大。
     2. **日常开发与个人高频迭代（顾问分层模式）**：主执行流挂载中等成本高速度模型（如 Sonnet 或 `Qwen3.8-27B` + `reasoning_effort=low`），配置关键节点升级机制（类似 `/advisor opus`），仅在「方案设计前、同一报错连续出现 2 次以上、准备提交宣告完成前」唤醒旗舰模型介入审查。
     3. **ToB 企业客户生产交付（SLA 稳定压倒一切模式）**：砍掉一切海外易封号、易受网络波动影响或激进压缩上下文的模型，底层基模锁死国内高稳定商业 API（DeepSeek / GLM 系列），确保早高峰零 `403`、零断连。
   - **如果 `task_goal == protocol_decoupling`（Agent 客户端与模型解耦）**：
     1. 在本机启动协议转换代理（如 `OpenCodex` 监听 `127.0.0.1:10100`），将客户端（Codex / Claude Code）锁死的 `Responses API` / 专有格式双向映射为标准 `Chat Completions` 或目标厂商协议；
     2. 或使用统一网关配置表（如 `magpie` Agent 面板）将各 Agent 的 `provider/model` 抽离为单键配置，验证在不重启工作流的前提下切换底层模型。
   - 完成标准：已输出明确的参数矩阵、路由规则表或代理配置方案。

2. **执行风险与反作弊核查**
   - **如果用户在评测中让 Agent「跑 10 次并生成统计报告」却发现 Agent 在上下文中手算或提前偷懒退出 → 将任务改写为由外部 Harness 脚本强制循环调用 10 次并收集日志，不在单次 Prompt 内考验模型的计数器耐心。**
   - **如果用户计划用便宜/早期模型先写一套详细的产品技术 Spec 再交给强模型写代码 → 立即拦截并告警「早期智商债」风险，要求删减为纯要点列表（Key Points）后再交由 SOTA 模型直接实现。**
   - **如果用户看到某模型在第三方榜单（如 Artificial Analysis）分数突然暴跌 → 先核查榜单是否更换了考纲标准，再用本机 6 连抽或产物基准复测，不盲从榜单波动。**
   - 完成标准：所有算力陷阱与评测偏差均已附带缓解措施。

## B — 适用边界与反例 (Boundaries & Counter-examples)

### 适用前提
- 团队或个人需要在多个模型/Agent 之间做工程选型、控制每月数百美元的订阅/API 账单，或需要向客户提供可承诺 SLA 的 AI 系统。
- 具备运行基础基准脚本或查看本地代理端口的工程环境。

### 不适用场景 / 常见误用
- **误用 1：拿单一后端跑分外推全栈能力** — `@karminski3` 明确划定边界：`vector-db-bench` 只反映后端 Agentic Coding 能力，绝对不能外推到前端审美（如 3D / 光影特效 Kimi-K3.1-Pro 反而更强）或通用日常对话。
- **误用 2：迷信 `reasoning_effort=max/xhigh` 必出最优结果** — 实证论文（`arXiv:2506.04210`）与小模型竞技场实测均表明，过度思考（Overthinking）会导致性能先升后降，且厂商常拿 `max` 档刷榜、把天价计费风险转嫁给用户；在多数日常 Agent 编码中，`low` 或 `medium` 档配合正确的 Harness 反而更快更准。
- **误用 3：把 Skill 写成只会处理固定格式的死文档** — `@karminski3` 警告：如果给 Agent 的 Skill 只是写死几种格式说明，遇到未见过的格式就会当场报错崩溃；真正健壮的 Agent 能力必须保持「代码/数据同构」，让模型能现场写代码做元编程解析。

### 自检清单
- [ ] 横向对比多个模型时，是否已锁死完全一致的 `reasoning_effort` 档位与系统提示词？
- [ ] 前端或生成类评测是否已执行「同一 Prompt 连跑 6 次」以检验稳定性，而非只挑最好的一次截图？
- [ ] 长线维护的核心仓库是否已禁止 AI 生成冗长 Spec、只保留关键 Points 以防范「早期智商债」？
- [ ] 面向企业客户的线上服务是否已切换为高稳定基模（如 DeepSeek/GLM），排除了 403 封号与跨国网络抖动风险？
