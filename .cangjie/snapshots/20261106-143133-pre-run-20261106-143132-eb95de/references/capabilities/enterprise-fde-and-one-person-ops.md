## I — 方法论骨架 (Interpretation)

把 AI 真正落进企业业务或一人公司日常运营，最大的死因从来不是「模型不够强」，而是**选错了切入点、错估了旧系统改造成本、或者放任 AI 在无人监管的闭环里裸奔**。无论是给传统企业做 FDE（Forward Deployed Engineer，前线部署工程师）交付、推动成熟公司向 AI Native 2.0 转型，还是搭建一人公司的极简赚钱机器，都必须遵循「先算地基账与控制颗粒度 → 岗位 Agent 化与数据留痕 → 关键风险处设代码/人工硬闸门」的三层架构：

1. **对外企业 FDE 交付（筛客户 + 控工期 + 外围切入 + 三层报错）**：
   - **商业与范围风控**：FDE 不是卖炫酷 Demo，而是「咨询诊断 + 技术实施 + 培训陪跑」的苦差事。面对传统制造业，必须先用 **5–8 万元/系统的地基成本**（对接 CRM/SRM/ERP/MES/WMS 的接口改造费）筛掉只想花小钱买 AI 的劣质客户；5 人以下小团队单次合同严禁超过 **20 个人天**。
   - **非敏感外围破局与术语降维**：面对顾虑数据安全或妄想「一键全自动对账」的传统老板，先从不涉密的「外围四件套」（做海报、写公开宣传文案、做 PPT、整理公开资料）切入；把业务拆细，只将「无需判断或判断标准可量化」的环节交给 AI；沟通时彻底去黑话（Skill 叫「能力/技能」、Agent 叫「数字员工」、MCP 叫「服务」）。
   - **三层报错兜底机制**：涉钱涉账流程（如多银行流水导入对账）必须建立「**代码层报错 → Agent 检查层报错 → 人工验证**」，把漏拉接口、重复导入导致余额错位等已知异常直接写进确定性代码脚本，在第一层拦截 80% 以上的错误。
2. **对内组织与高管 AI Native 2.0（高管审核制 + 岗位 Shared Bot + 封闭生态视觉长程执行）**：
   - **高管审核制与岗位重构**：把飞书审批、消息、邮件全交由 Agent 预处理并生成呈批件，管理者退居二线只做最终复杂审核与改进 Agent；将散落在个人聊天里的提示词提炼为团队共享、可一次更新的「岗位级 Shared Bot」（必须配齐四要素，并在发稿/上线前设置飞书人工审稿闸门）。
   - **无接口生态与跨端事务接管**：针对个人微信等无 API、加密防截图的封闭生态，采用电脑端视觉代理按「搜人→核对身份→读上下文→拟稿→人工确认→发送→看回复续聊」长程执行；跨端采购用自带虚拟机浏览器的 Agent（如 Muse）比价装购物车，结合线下超市小票拍照自动剔除已购品防重买，最后由本人手机端点击付款；非专业设计岗用轻量支持 Agent 读写目录的开源工具（如 12MB 的 Compositor）替代全员高价 Adobe 订阅。
3. **一人公司极简底座与转化闭环（三件套 + 索引式知识库 + 四源留痕 + 收银台直达召回）**：
   - **极简工作台与防乱知识库**：日常工具收敛为「微信 + Chrome + Agent」三件套；为防止 AI 直接修改本地库导致目录混乱，采用「**本地目录索引（分类/标题/链接）+ 云端 Notion 正文**」的轻量自生长知识库（LLM Wiki），辅以「微信 CLI + 本地 Agent 会话 + QQ 导出 + 文件修改历史」四源个人数据本地化沉淀，国内高风控社媒（小红书/抖音）则用浏览器插件在人工浏览时被动采集。
   - **支付召回抓转化细节**：SaaS 网站监听 Stripe 未付款事件发召回邮件时，决胜点不在文案而在跳转链接——有恢复链接直达收银台，无恢复链接则跳回充值页并自动预填上次金额与支付方式，且发信前必须挂载 `expired/completed` Webhook 防止向已付款用户重复发信。

## A1 — 应用示例 (Application Example)

### 示例 1: 传统企业 FDE 落地：用「5–8 万地基成本」筛客户与银行流水「三层报错」
- **类型与来源**: 原书实操案例（`@cnzhihao` `2026-10-26` / `2026-10-28` 帖文 + `@jinchenma_ai` `2026-10-28` / `2026-10-30` / `2026-11-01` 帖文）
- **问题/输入**: 一家传统制造/电商企业老板找到 FDE 团队，要求用一个 AI Agent 把订单、退货、物流、库存、多银行流水收款对账一次性全自动串起来，但只愿出几千到一两万的「搭 AI 费」，且高度戒备核心财务数据外泄。
- **方法论的使用**:
  1. **商业筛选与拆单**：先算清制造业「地基成本」——单接通一个 ERP/MES/WMS 系统接口就要 5–8 万元，若客户只想付搭 Agent 的钱直接拒单；签约时将首期范围严格卡死在 **20 个人天**以内。
  2. **外围切入与术语降维**：针对数据安全顾虑，首期先用「非敏感外围四件套」（宣传海报、公开文案、PPT、公开资料整理）或本地桌面办公 Agent（WorkBuddy）建立信任；沟通时将 Agent 称为「数字员工」、Skill 称为「技能」。
  3. **三层报错架构落地财务对账**：拒绝让大模型裸算账目，搭建「代码层报错（硬编码校验是否漏拉某家银行接口、是否重复导入同一份流水导致余额连续错位，拦截 80%+ 异常）→ Agent 检查层报错（语义核对摘要与科目）→ 人工最终验证」的三层防线。
- **结论**: 企业 FDE 拼的是业务流程拆解与确定性兜底，用代码守住账目底线、用人工守住责任边界。
- **结果**: 成功过滤掉烂尾亏损单，落地项目的账目异常在代码层即被精准捕获，培训与陪跑客单价稳定在 2–3 万元。

### 示例 2: 上市公司 CEO 的「一周不登飞书审核制」与微信 120+ 条消息零失误长程接管
- **类型与来源**: 原书实操案例（`@FuSheng_0306` `2026-09-26` / `2026-10-23` / `2026-10-27` 帖文）
- **问题/输入**: 成熟企业高管每天被海量的飞书审批、邮件、节日微信人脉维护（50 位核心骨干定制祝福及后续互动）和跨平台家庭/办公采购淹没，而个人微信无开放接口且防系统级截图，传统群发脚本既冰冷又有封号风险。
- **方法论的使用**:
  1. **飞书与邮件行「审核制」**：所有审批、消息、邮件先由专属 Agent 汇总上下文并拟好处理意见，高管一周不登飞书，只审阅 Agent 呈批件并借此反推各部门将岗位升级为「人做复杂审核 + 持续改进 Agent」（AI Native 2.0）。
  2. **微信端走视觉代理 + 人工闸门**：让电脑端视觉 Agent 模拟真人操作，严格执行 7 步循环：`搜人 → 核对身份 → 读历史聊天上下文 → 撰写千人千面定制祝福 → 停下等本人确认 → 点击发送 → 盯屏幕看对方回复并继续接话`。
  3. **跨端采购防重买**：用 Muse 虚拟机浏览器在 HKTVmall 与京东自动比价装购物车；线下逛完超市后拍一张纸质小票发给 Muse，自动比对并从线上购物车剔除已购商品，最后由本人在手机端看一眼点付款。
- **结论**: 模拟人工速率 + 结合聊天上下文定制 + 发送/付款前保留最后一道人工确认闸门，即可在零 API 的封闭生态中安全撬动数千步长程自动化。
- **结果**: 连续数小时执行几千个细小动作、收发 120+ 条中秋微信消息（50 条定制祝福 + 70+ 条回复互动）零发错、零封号，且中途人工打断后能无缝续接。

### 示例 3: 一人公司「本地索引+云端正文」知识库与 Stripe 直达收银台召回流
- **类型与来源**: 原书实操案例（`@jinchenma_ai` `2026-10-31` / `2026-11-04` 帖文 + `@sitinme` `2026-10-30` / `2026-11-03` 帖文 + `@icycat` `2026-10-20` / `2026-10-21` 帖文）
- **问题/输入**: 独立开发者/一人公司在运营多个出海网站与自媒体时，直接让 AI 按 Karpathy 的 LLM Wiki 方案读写本地 Obsidian 库会把目录改得一团糟；同时网站有大量用户在 Stripe 结账页放弃付款，常规营销召回邮件转化极低。
- **方法论的使用**:
  1. **构建防乱自生长知识库与四源留痕**：放弃重度 RAG，本地只维护「分类 + 标题 + 链接」的轻量目录索引（Obsidian 仅作只读浏览器），正文全部存入云端 Notion 由 AI 归纳入库，Agent 干活时「先查本地索引 → 再按链接拉取云端正文」；同时用脚本定期将「微信 CLI 相关会话、本地 Agent 历史会话、QQ 聊天导出、本地文件修改记录」四源数据总结入库，小红书/抖音素材则通过自研 Chrome 插件在人工刷帖时被动落库。
  2. **岗位级 Bot 加飞书审稿闸**：配置共享推文 Bot，每天定时从素材库挑题写分享体草稿，投递至飞书审稿群后自动挂起等待人工拍板。
  3. **改造 Stripe 未付款召回链路**：监听未付款事件，发信前先挂载 `expired` 与 `completed` Webhook（一旦用户已付或链接过期立即停发）；邮件内若有 Stripe 会话恢复链接则直达收银台，若无则跳回站内充值页并在 URL 参数中默认锁定用户上次选择的金额与支付方式。
- **结论**: 一人公司的效率来自「索引与正文分离」的低维护上下文，而变现效率来自把摩擦降到零的直达收银台链接与关键人工闸门。
- **结果**: 知识库底座实现零混乱自生长并开源复用；出海站点未付款订单召回率显著提升，一人凭「微信 + Chrome + Agent」三件套即可闭环运转。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?
1. **传统企业 AI 落地（FDE）接单与排障**：用户准备给企业客户做 AI 咨询或 Agent 交付，不知道怎么评估报价、怎么防需求蔓延、怎么切入怕泄密的传统老板，或者在财务/ERP 数据对接中经常遇到 AI 算错账。
2. **高管办公减负与 AI Native 组织改造**：公司管理者想把飞书审批、邮件、微信客户沟通或采购流程交给 Agent 托管，或者想重构团队岗位职责、削减全员高价软件订阅（如 Adobe 全家桶）。
3. **一人公司工作台与个人知识库/数据沉淀**：独立开发者想用最精简的工具栈管好多个渠道、搭建不会被 AI 改乱的个人知识库（LLM Wiki）、沉淀微信/QQ/Agent 全量个人记忆，或采集小红书/抖音高风控平台内容。
4. **出海 SaaS 支付漏斗召回与运营自动化**：用户的网站接入了 Stripe，发现大量未完成支付订单，或者想把个人的内容生产流程变成团队可共享的岗位级 Shared Bot。

### 语言信号 (用户的话里出现这些就应激活)
- 「怎么做企业 FDE」「给传统企业做 AI 落地怎么报价 / 怎么防坑」「制造业接 AI 要多少钱」
- 「AI 导银行流水 / 对账老出错怎么办」「代码层 Agent 层人工三层报错」
- 「怎么用 Agent 管飞书审批和微信回复」「什么是高管审核制 / AI Native 2.0」「怎么防止线上线下重复买东西」
- 「LLM Wiki 把我本地 Obsidian 改乱了怎么办」「一人公司怎么搭工作台和知识库」「怎么把微信和 Agent 聊天记录沉淀下来」
- 「Stripe 未付款怎么发召回邮件」「怎么做岗位级 Shared Bot」

### 与相邻 skill 的区分
- 与 `agent-software-factory` 的区别：`agent-software-factory` 解决的是纯代码研发环节的并发编译（Git Worktree / Xcode CAS）与代码审查；本能力卡解决的是面向企业甲方的商务交付边界、组织审批流改造、个人知识库与收款召回运营。
- 与 `seo-geo-growth-engine` 的区别：`seo-geo-growth-engine` 负责把外部搜索与 AI 引用流量引进网站（URL 规划、TDH、Fan-out 选题）；本能力卡负责流量进站产生未付订单后的 Stripe 链接召回，以及背后的岗位 Bot 与一人公司运营底座。

## E — 可执行步骤 (Execution)

**必需输入**:
- `scenario_type`（必填，枚举：`enterprise_fde` [企业 FDE 交付] | `exec_ai_native` [高管审核制与组织转型] | `one_person_ops` [一人公司知识库与转化召回]）
- `business_context`（必填：企业 FDE 需说明客户行业、现有系统［ERP/MES/表格］与团队人数；高管/组织需说明日常高频办公软件与痛点岗位；一人公司需说明当前笔记/数据源与收款渠道）
- 若用户要求在微信群发、财务打款或公开发布环节「完全跳过人工确认直接全自动执行」，必须触发安全拦截并先输出带人工确认闸门的方案。

**交付物与完成标准**:
- 企业 FDE 报价与准入评估表 + 三层报错架构设计、高管审核制与岗位 Shared Bot 配置规范（含人工闸门）、或一人公司「本地索引+云端正文」知识库目录结构与 Stripe 召回链路方案。

当此能力被激活后，按以下步骤执行：

1. **诊断场景并划定商业与安全准入红线**
   - **如果 `scenario_type == enterprise_fde`（对外企业 FDE 交付）**：
     1. **核算地基成本筛客户**：先盘点客户需求是否依赖底层业务系统（CRM / SRM / ERP / MES / WMS）。每涉及一个未打通系统的接口改造，按 **5–8 万元/系统** 计入前置「地基成本」；若客户只愿支付表层 Agent 搭建费而拒绝承担地基成本，直接建议拒单或退回纯本地表格方案。
     2. **锁死工期与切入点**：当交付团队 ≤5 人时，单份合同工期硬性卡死在 **≤20 个人天**；对数据敏感的传统客户，首期强制收敛为「不涉密外围四件套」（海报、公开宣传文案、PPT、公开资料整理）或本地桌面 Agent（如 WorkBuddy），沟通话术全部替换为下沉市场白话（数字员工 / 技能 / 服务）。
     3. **部署三层报错机制**：将业务流程拆分为子环节，仅对「无需判断或判断标准可量化」的环节自动化，并按三层实现异常拦截：
        - **第一层（代码层报错，拦截 80%+ 异常）**：用确定性脚本校验数据源完整性（如是否漏拉某家银行接口、是否重复导入同一批次流水号、期初与期末余额是否连续咬合）；
        - **第二层（Agent 检查层报错）**：由 Agent 对通过代码校验的数据做语义与科目合理性复核，标记可疑条目；
        - **第三层（人工验证）**：由业务负责人对最终汇总表与异常清单签字确认。
   - **如果 `scenario_type == exec_ai_native`（高管审核制与组织 AI Native 2.0）**：
     1. **建立高管审核制**：将飞书审批、消息、邮件接入预处理 Agent，统一生成含「背景上下文 + 风险点 + 建议动作」的呈批摘要，将管理者的动作从「逐条翻找处理」压缩为「每日集中批复呈批件」。
     2. **封装岗位级 Shared Bot**：将各岗位（如销售情报、报价单生成、早报/推文起草）散落的个人 Prompt 集中封装为团队共享 Bot，强制补齐四要素：**明确角色边界、授权白名单与触发规则、标准输入输出模板、可集中更新的共享知识/技能库**。
     3. **封闭生态视觉长程执行与跨端防重购**：对个人微信等封闭端，采用电脑端视觉 Agent 按「搜人 → 核对身份 → 读上下文 → 拟定制稿 → **人工确认闸** → 发送 → 读回复续聊」执行，严禁使用改密码或高频群发外挂；对跨端采购，用自带虚拟机浏览器的 Agent 比价加购，并接入线下小票拍照识别自动剔除已购项，最终付款保留在本人手机端完成；对非专业岗位的轻量修图/互动需求，评估用支持 `.comp` 目录实时读写的开源工具（如 Compositor）替代全员高价商业软件订阅。
   - **如果 `scenario_type == one_person_ops`（一人公司工作台与支付召回）**：
     1. **搭建「本地索引 + 云端正文」自生长知识库**：在本地仅建立轻量 Markdown 目录索引（记录分类、标题与云端 URL，Obsidian 仅作只读视图），将长篇正文存储在 Notion 等云端文档中由 AI 归档；配置 Agent 检索协议为「先读本地索引定位条目 → 再按链接按需拉取正文」，彻底杜绝 AI 写坏本地库结构。
     2. **接入四源个人数据留痕与被动采集**：配置定期任务汇总 ① 微信 CLI 相关会话总结、② 本地 Agent 历史会话沉淀、③ QQ 聊天导出总结、④ 本地文件修改历史；针对小红书/抖音等严风控平台，放弃主动爬虫，改用浏览器扩展在人工搜索浏览时被动归档素材。
     3. **部署 Stripe 未付款直达召回流**：
        - 前置钩子：先接通 Stripe 的 `checkout.session.expired` 与 `checkout.session.completed` Webhook，确保已付款或已失效订单立即移出召回队列；
        - 链接构造：召回邮件中若存在有效恢复 URL 则直接指向 Stripe 收银台；若原会话已过期，则生成带查询参数的充值页链接，自动预填该用户上次选择的**金额档位与支付方式**。
   - 完成标准：已按对应场景输出完整的落地方案、目录结构或代码/流程防线。

2. **核查关键人工闸门与风控闭环**
   - **如果自动化工作流涉及对外发布内容、微信发送消息或资金扣款，但流程图中没有显式的人工暂停确认节点 → 立即在生成草稿/装入购物车之后插入「飞书审稿群/手机端人工确认闸」，规定自动任务在此挂起，未收到人工指令严禁外发。**
   - **如果客户属于大型集团、国企或政府部门且新团队准备按 20 人天标准接单重度开发 → 立即发出红灯预警（`@cnzhihao` 实证：此类机构审批与政治流程极重，新手团队极易被拖死），建议仅提供标准化培训或直接放弃。**
   - **如果一人公司准备用 AI 直接全量改写本地数千篇笔记构建 LLM Wiki → 立即切换为「只生成本地索引清单、不动原文文件」的安全模式。**
   - 完成标准：所有高危外发、扣款与文件修改节点均已配置确定性保护闸门。

## B — 适用边界与反例 (Boundaries & Counter-examples)

### 适用前提
- 企业 FDE 场景下，甲方有真实的业务降本增效诉求，且愿意配合梳理现有流程；一人公司与高管场景下，使用者愿意从「亲手操作每一步」转向「定义规则与把控最终审核闸门」。

### 不适用场景 / 常见误用
- **误用 1：新手小团队硬接大型集团/国企/政府的重度定制开发单，或接超过 20 人天的长单** — `@cnzhihao` 明确警告：大型机构流程极其繁琐，且动辄把 FDE 当成「给全公司重装杀毒软件、买交换机、拉网线建防火墙」的廉价网管；5 人以内团队一旦签下超 20 人天的包干单，极易因需求蔓延而严重亏损。
- **误用 2：在 Vibe Coding 中炫技式「一天干完客户内部团队两三个月的活」并当众邀功** — `@cnzhihao` 提醒企业交付必须懂组织利益：别人十几个人做两三个月的系统被你一天干完，直接触动内部团队饭碗，项目极易遭到内部联合抵制甚至被解约。
- **误用 3：在小红书、抖音等强风控平台使用主动 Agent 爬虫批量抓数据，或在微信使用非模拟人工的协议外挂** — `@icycat` 实测小红书用主动自动化弄两下即弹严重警告，必须改用浏览器插件配合人工浏览做被动收集；`@FuSheng_0306` 亦强调微信自动化必须按正常人工频率模拟操作并留人工确认，绝不能用接管账号改密码的黑产玩法。
